# mac-lookup アーキテクチャ

この文書は各要素が **なぜ** その形なのかを記録する。各パッケージが何をするかは
[AGENTS.md](../../AGENTS.md)、決定の経緯は [RFP](mac-lookup-rfp.ja.md) にある。

## 中核の判断 — 「種別判定」こそが製品である

このツールの素朴な実装は OUI からベンダー名へのハッシュマップである。しかし
それは独立した 2 つの理由で、危険なほど頻繁に誤答する。

**Locally Administered なアドレスには製造元が存在しない。** iOS 14 / Android 10
以降、スマートフォンは接続するネットワークごとに異なるランダム化 MAC を提示する。
仮想 NIC、コンテナブリッジ、VRRP の仮想ルーターも同様で、いずれも U/L bit を
立てる。ベンダー表はこれらについて何も語れない。問題は失敗の仕方である
——「ベンダー不明」は *見つけられなかった* と読め、さらに探すことを促す。
しかし真実は *探すべきものが存在しない* である。この違いを知らない調査者は、
10 分前に合成され明日には捨てられるアドレスの相関に何時間も費やす。

したがって種別判定は無条件に先行する: broadcast → I/G bit（multicast。
プロトコル用の小さな表から名前を付ける）→ U/L bit。レジストリを引くのは
Universally Administered の場合だけである。出力が
`vendor_lookup_applicable` を第一級のフィールドとして持つのは、呼び出し側が
この 2 つのケースを暗黙に混同できないようにするためである。

**1 つの OUI を複数のベンダーが保有しうる。** IEEE は 24bit ブロック(MA-L)を
販売する一方、それを 28bit(MA-M) や 36bit(MA-S、歴史的には IAB)に細分して
割り当てる。36bit の割当は、別の組織も現れうる 24bit プレフィクスの内側にある。
先頭 6 桁で照合すると、もっともらしく整形された **誤ったベンダー名** が返る。
照合は最長一致、36 → 28 → 24 の順である。

`macaddr` は種別判定を担いレジストリを一切知らない。`ouidb` はレジストリを
担い種別判定を一切知らない。両者を分けることで、意味論的に微妙な部分が
純粋・小規模になり、データファイルなしでテストできる。

## なぜ API ではなくオフラインキャッシュか

依存に値する MAC ベンダー API はそもそも存在しないが、仮にあったとしても、
データセット全体が 5.6 MB・約 58,000 行である。一度落としてメモリ上で照合する
方がどんなクライアントより単純で、索引も要らない。そして決め手は、**照会が
一切の通信を発生させない**ことである。インシデント対応中に、いま観測した
アドレスを第三者に問い合わせる行為は、その第三者に調査内容を伝えてしまう。
このシリーズ（`asn-lookup` / `tor-exit-lookup` / `icloud-relay-lookup`）が
同じ取引をしているのも同じ理由による。

## なぜ認証情報を持たないか

IEEE のファイルは公開されている。これは些細な利便性ではない。トークンを持たない
ツールには、設定すべきものも、ローテーションすべきものも、ログに漏らすものも、
調査の最中に失効するものもない。設定スキーマに認証項目が存在しないため、
うっかり追加されることもない。

## 取得時の挙動と 418

2026-07-26 に実測した IEEE 側の 2 つの性質が、フェッチャの設計を決めている。

各レジストリファイルは `ETag` と `Last-Modified` を返す。したがって更新が
なかった再取得は 5.6 MB ではなく `304` で済む。ファイルの再生成が概ね日次で
あるため、TTL の既定は 24 時間、下限は 6 時間とした。それ以上の頻度で叩いても
新しいものは出てこず、他人の帯域を消費するだけである。

より意外なのは、この origin が **ブラウザを騙るリクエストを拒否する** ことだ。
`User-Agent: Mozilla/5.0` には `418 I'm a Teapot` が返り、素のクライアント UA
は正常に配信される。スクレイパを偽装するという通常の直感が逆転している。
`ieee.UserAgent` はツール名とリポジトリ URL を名乗る——正直であることが、
同時に唯一動作する方法でもある。

## 決定性と鮮度

シリアライズは明示的なタイムスタンプを受け取りエントリをソートする。よって
時計を読むのは `engine.Update` だけであり、同じ入力からバイト単位で同一の出力が
得られる（diff できるストア）。書き込みは一時ファイル + rename を経るため、
中断された更新が「小さいレジストリとして正常にパースできてしまう」半端な
キャッシュを残すことはない。

鮮度はファイルの mtime からの推測ではなくレコード内(`generated_at`)に保持する。
コピー・同期・リストアによって 1 年前のスナップショットが最新に見えることを
防ぐためである。

## 意図的に持たないもの

- **第三者の集約ベンダーリスト**（Wireshark の `manuf` 等）。部分的には
  よく整備されているが、このリポジトリに伝播するライセンスを伴う。IEEE 原本のみ。
- **能動スキャン**。本ツールはフレームを 1 つも送出しない。既に捕捉したものを
  解決するだけである。
- **登録住所からの国コード抽出**。一貫した構造を持たないフリーテキストであり、
  抽出した `country` はそれを基にした集計を汚染する程度には頻繁に誤る。
  住所は原文のまま保持する。
- **BSSID 群解析**（近接 BSSID から同一 radio を推定する機能）。有用だが
  本質的にヒューリスティックであるため v0.2 に送る。精度検証の作業が、
  正確な単一アドレスリゾルバの完成を遅らせないようにするためである。
